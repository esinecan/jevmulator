# Jevmulator target contract — pinned 2026-09-22

The provider publishes a usable machine-readable contract at **https://api.typesafe.ai/openapi.json**. We can pin Jevmulator's HTTP surface to that snapshot. TypeSafe also publishes its own OpenAI-compatible LLM adapter; it is useful implementation material, but it is a Python client library, not a Jev HTTP server. Exact production confidence, numerical rounding, token accounting, and several error behaviors remain unverified.

## HTTP surface

| Method/path | Request | Success |
|---|---|---|
| `POST /v1/systemone` | JSON `SystemOneRequest` | `200 application/json`, `SystemOneResponse` |
| `GET /v1/models` | No body | `200 application/json`, `ModelMetadataList` |

Provider root is `https://api.typesafe.ai`. Both endpoints declare HTTP bearer authentication: `Authorization: Bearer <API_KEY>`. POST sends `Content-Type: application/json`; SDKs also send `Accept: application/json`. No chat-completion envelope or streaming contract appears in this API. No temperature, seed, tools or conversation endpoint is part of the pinned surface.

SDKs add identification headers (`User-Agent`, `X-TypeSafe-SDK`, `X-TypeSafe-Runtime`) and `X-TypeSafe-Retry-Count` on retries. These are client behavior, not documented mandatory authentication fields. Both SDKs recognize `x-typesafe-request-id` on responses. They recognize `retry-after` and `retry-after-ms`; header existence, exact formatting and generation rules are not guaranteed by the OpenAPI document. No response `id`, `object`, `created` or `choices` field is required.

## Input schema

Here, **content** means a JSON string, object or array. An object's values and an array's members may be arbitrary JSON values, including nested numbers, booleans and nulls. This does not permit a top-level number or boolean where content is required.

| Field | Exact published OpenAPI rule |
|---|---|
| `state` | Required content; top-level null is excluded. No length minimum in schema. Empty string/object/array are schema-valid, with runtime behavior unverified. |
| `model` | Required string, no schema default or enum. SDK default is `jev-latest` and is explicitly inserted before transmission. |
| `questions` | Required object with at least one property. Arbitrary string IDs map to discriminated `Question` objects. No schema maximum count or ID length. |
| Every question's `type` | Required exact string `noul`, `choice` or `score`; discriminator selects the branch. |
| Every question's `instructions` | Optional content **or null**. The HTTP prose page instead marks it required; OpenAPI and both SDKs agree on optional/null. The OpenAPI does not assign an explicit default; Python convenience objects default to `None` and omit it. |
| Choice `criteria` | Required object: arbitrary option string → content or null. Null means description omitted. OpenAPI has no minimum/maximum property count. Docs impose a maximum of 255 options. |
| Score `criteria` | Required array of content, `minItems: 1`, no schema maximum. Null/scalar numeric/boolean level descriptions are excluded. Position is the numeric level, starting at zero. Docs recommend at least two levels and say API accepts up to ten. A one-level score is schema-valid; runtime acceptance is not verified. |
| Noul `criteria` | Optional object or null. Object has optional `true` and `false` fields, each content or null. Neither must be present. |

No top-level request/question schema sets `additionalProperties: false`; JSON Schema validation therefore permits unspecified properties. This is not proof that the service preserves or uses extras. Python question convenience classes forbid extras, while raw dictionaries can be passed through more permissively. Do not infer server behavior from that SDK difference.

The model is text-only. Images, audio and video require conversion to text/structured fields before calling it. Current model docs describe **64k tokens for state plus all questions, and 32k tokens for state plus the longest question**. This is a documented semantic limit absent from the JSON schema; the exact tokenizer and rejection details are unpinned. Published current rate limits are 250,000 tokens/second and 1,200 requests/minute, explicitly subject to change and account plan; they are deployment policy rather than durable schema.

## Output schema and semantics

`SystemOneResponse` requires `model: string`, nonempty `answers: object`, and `usage: object`. Each answer is keyed by the exact submitted question ID and carries the matching discriminator. Required usage fields are **integer `input_tokens` and integer `output_tokens`**. Null or missing counts are tolerated by the Python public SDK, but are excluded by the provider's wire schema. No schema minimum is attached to these integers; semantically they are token counts.

| Answer | Required fields and types | Documented semantics |
|---|---|---|
| Noul | `type: "noul"`, `noul: number` | P(yes), range 0–1. No separate confidence property. |
| Choice | `type: "choice"`, `choice: string`, `confidence: number`, `probabilities: object<string, number>` | Chosen option is a highest-probability supplied option; full supplied option distribution. Confidence in 0–1. Tie-breaking rule undocumented. |
| Score | `type: "score"`, `score: number`, `confidence: number`, `legend: object<string, content>`, `probabilities: object<string, number>` | Expected value `sum(i * p_i)` over zero-based levels, potentially fractional. Legend repeats each original structured description. Probability keys match legend keys (`"0"`…`"N-1"`). Confidence in 0–1. |

The OpenAPI descriptions say probabilities sum **approximately** to one. The schemas themselves use `number` without min/max or sum constraints; response/request correspondence and range checks are semantic checks to run separately. Exact decimal precision, rounding mode, tolerance, whether score is computed before or after rounded probabilities, and tied-choice selection remain unverified. Do not silently equate rounded published maps with exact underlying distributions.

Extra response fields are schema-permitted. The Python SDK ignores unknown properties and even discards unrecognized future answer types; this is forward-compatible parsing, not permission for Jevmulator to omit requested answers. The SDK converts score map keys to integers in Python; the HTTP JSON keys remain strings.

Every question sees the same state and is evaluated independently. Adding or removing a question must not change another question's evaluation; answers do not become hidden context for each other. Question IDs are routing labels and **are not supplied to the underlying model or used in inference**. Choice labels, unlike question IDs, are semantic input when a description is absent. [Official semantics](https://docs.typesafe.ai/primitives), [ID semantics](https://docs.typesafe.ai/api).

## Models and versioning

`GET /v1/models` returns `{ "models": [...] }`, each entry requiring string `name`, `description`, `release_date`; the latter is described as `YYYY-MM-DD` but has no schema format constraint. Current docs list aliases `jev-latest` and `jev-preview`, both resolving to `jev-1.13.0`. Versioned IDs may be accepted even if discovery lists only aliases. A successful response reports the versioned model used according to the model docs. No live authenticated discovery was performed.

Pin Jevmulator's **contract profile** to the OpenAPI hash/date and SDK versions above, separately from upstream GLM model configuration. Do not follow changing docs or `jev-latest` automatically. Refresh into a new dated snapshot, diff schema and semantic assertions, then rerun consumer and SDK conformance before adopting. A synthetic emulator must document its model-name/alias mapping rather than imply its GLM output came from TypeSafe weights.

## Errors

Official HTTP prose specifies 401 (missing/invalid bearer key), 422 (request validation), 429 (rate limit), 529 (overloaded). OpenAPI only enumerates 200 and 422; it does not deny that other documented statuses occur.

The 422 body is `HTTPValidationError`: optional `detail: array<ValidationError>`. Each validation entry requires `loc: array<string|integer>`, `msg: string`, `type: string`; optional `input` is unrestricted JSON and optional `ctx` is an object. Exact error strings, validation ordering and field path details are not established by examples. Non-422 error bodies have no published pinned schema.

SDK error parsers accept several envelopes (`error.message`, string `error`, top-level `message`, string/object/list `detail`). This is defensive client handling, not evidence that TypeSafe emits all these forms. SDKs retry connection/timeouts and HTTP 408, 429 and 5xx by default, with two retries after the initial attempt and exponential backoff; 529 is included. A daemon should deliberately map backend failures and validation failures, but exact TypeSafe error parity cannot yet be claimed.

## Conflicts resolved by keeping layers separate

| Apparent contradiction | Pinning decision |
|---|---|
| HTTP prose marks instructions required; OpenAPI/SDK make them optional/null | Wire target accepts omission/null. Preserve this regression case. |
| HTTP prose narrows Score legend to string; OpenAPI/SDK allow structure | Wire target preserves object/array descriptions. |
| JavaScript permits null state and null Score descriptions; OpenAPI excludes both | Use OpenAPI for server acceptance. SDK static types are broader than the wire target. |
| Python public response allows absent/null usage and defaults absent answers to empty | Server success uses required integer counts and required nonempty answers. |
| Score docs say at least two; schema says minItems one | Schema permits one; recommend two–ten; runtime one-level behavior is an explicit open gap. |
| Numeric range and option limits appear in prose, absent in schema | Keep a separate semantic conformance suite; do not mislabel stricter derived schema as the vendor schema. |
| Old SDK before 0.6 used integer-keyed Score criteria dictionary | Current pin uses ordered array; legacy input is a separate version feature, not silently added. |

## Official adapter: reusable work and limits

[TypeSafe's System One Adapter](https://github.com/typesafe-ai/system-one-adapter-python/tree/e1d4cc938204b22fc5a3c3aca7044072fe3f712d) supplies `SystemOneAdapterClient` and `AsyncSystemOneAdapterClient`. `from system_one_adapter.providers.openai import OpenAIProvider` provides `OpenAIProvider(model, base_url=...)`; custom endpoints default to Chat Completions and can explicitly select `api="chat_completions"`. Its client supports native structured output or prompted JSON with validation, probability/discrete modes, normalization, corrective retries, and transient retries. It returns a `typesafe_sdk.SystemOneResponse` subclass, adding debug information and usage fields. These additions and nullable upstream usage must be translated before emitting the pinned wire envelope.

It is **not an HTTP daemon** and does not supply the Jev authentication, `/v1/models`, HTTP error compatibility or endpoint hosting layers. Its collective question prompt is not proof of Jev's question independence/ID invisibility; Jevmulator must enforce those requirements itself if semantic compatibility is desired.

The official adapter exposes reproducible confidence algorithms in [confidence_metrics.py](sources/system-one-adapter-python/src/system_one_adapter/_utils/confidence_metrics.py):

- Normalize the distribution (zero total becomes uniform). One option/level returns confidence 1.
- Choice: `(max(p) - 1/N) / (1 - 1/N)`.
- Score: choose the first modal index `m`; compute `D = sum(p_i * abs(i-m))`; let `U = mean(abs(i-(N-1)/2))` across levels; return `max(0, 1-D/U)`.

These are **verified official adapter algorithms**, not verified production Jev algorithms. The confidence docs' interactive example uses the choice formula but explicitly calls it an approximation. Production confidence should remain an open semantic gap unless TypeSafe confirms the same formula or discriminating live examples establish it.

## Finite remaining gaps and acceptance gate

1. **Production numeric semantics:** confidence formula, rounding/precision and tie rules; GLM probability quality and calibration are separate evaluation work.
2. **Runtime validation edges:** one-level score, zero-option choice, empty content, extra fields, exact token boundaries and coercion behavior. OpenAPI supplies the schema baseline, not proof of every runtime outcome.
3. **Error parity:** current 401/422/429/529 bodies/headers, unknown-model behavior and backend failure mapping. 422 shape is published, exact messages are not.
4. **Token accounting and model identity:** TypeSafe tokenizer/billing counts cannot be reproduced from generic upstream usage without more information. Decide transparent emulator accounting and aliases before deployment.

Enough is pinned to implement and test schema compatibility now. Acceptance should validate complete request/response fixtures against **wire** schemas, enforce semantic correspondence separately, drive actual pinned Python and JS SDKs against a local fake transport/server, and run the retained consumer checks. Tests for unknown behavior must stay marked unknown instead of defining guessed TypeSafe behavior. Claim a pinned schema-compatible emulator first; claim complete behavioral parity only after the open gaps are resolved.
